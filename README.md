## Что это и какую задачу решает

Кейс трека 05 «Логистика»: автоматический расчёт заказов поставщикам. Менеджер получает количество к заказу по каждому SKU с объяснением влияния спроса, остатков, товара в пути и кратности. Решение об утверждении остаётся за человеком.

## Что реализовано

- Загрузка встроенных XLSX-выгрузок IEK и SE при запуске и загрузка собственного набора через интерфейс.
- Расчёт спроса с обработкой разовых продаж, месяцев без товара, сезонности и тренда; сравнение с Excel-методом.
- История SKU, объяснение рекомендации, правка итогового количества с проверкой кратности.
- Утверждение с записью в `var/approvals.json` и экспорт заказа в XLSX.
- Опциональная сводка через OpenAI-совместимый API; два подготовленных образца для исходных заказов лежат в `samples/cache/`.
- Бэктест прогноза на шести контрольных точках с марта по август 2026 года в `data/backtest/report.json`.

## Как устроено решение

```text
XLSX → ingest (parse) → engine (analyze или baseline) → API → React
                                     ↘ ai.summary → кэш/LLM
```

`app/ingest/` приводит выгрузки 1С к единому `Dataset`. `app/engine/` очищает спрос, восстанавливает спрос в месяцы без товара, прогнозирует и рассчитывает заказ. `app/api/` вызывает ядро, проверяет изменения менеджера и отдаёт JSON/XLSX. `app/store.py` держит наборы и прогоны в памяти. `frontend/` показывает параметры, строки заказа и историю SKU.

`analyze` учитывает очистку, stockout, сезонность и тренд. `baseline` использует среднее сырых продаж за последние 12 закрытых месяцев без этих поправок при той же политике остатка, товара в пути и кратности.

## Технологии и данные

Сервер: Python 3.12, FastAPI, Pydantic, pandas, NumPy, openpyxl. Интерфейс: React, TypeScript, Vite, TanStack Query, ApexCharts. Версии зафиксированы в `requirements.txt` и `frontend/package-lock.json`.

Данные — предоставленные для кейса выгрузки 1С в `data/raw/iek/` и `data/raw/se/` за 2024–2026 годы. Товарные группы в `data/categories/sku_categories.csv` получены правилами из названий и отдельным прогоном Laya: 3037 позиций определены правилами, 11 — моделью, 619 ответов модели отклонены из-за низкой уверенности. Замер приведён в `data/categories/laya_eval.json`. Модель онлайн-сводки задаётся переменной `MODEL`; два вложенных образца сводки сверены с текущим расчётом.

## Установка и запуск

На macOS в терминале zsh/bash из корня проекта нужна Python 3.12 (при отсутствии: `brew install python@3.12`). Одна команда создаёт окружение, ставит зависимости и запускает сервис:

```bash
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt && .venv/bin/python -m app
```

После сообщения о старте Uvicorn откройте `http://localhost:8000`. Проверка сервера: `http://localhost:8000/health` возвращает `{"status":"ok"}`. Node для запуска не требуется: собранный `frontend/dist` находится в репозитории.

Необязательные настройки задаются переменными окружения или копией `.env.example` в `.env`:

| Переменная | Назначение |
| :-- | :-- |
| `OPENAI_API_KEY` | Ключ LLM для новых сводок |
| `OPENAI_BASE_URL` | Адрес OpenAI-совместимого провайдера, в том числе NVIDIA NIM |
| `MODEL` | Идентификатор модели у выбранного провайдера |
| `PORT` | Порт сервиса; по умолчанию `8000` |

Для повторной сборки интерфейса на macOS в терминале zsh/bash: `cd frontend && npm ci && npm run build` (потребуется Node, поддерживаемый Vite 8). Для тестов из корня проекта: `.venv/bin/pytest -q`.

## Запуск без API-ключа

Сервис, расчёт `analyze` и `baseline`, правка и экспорт работают без `OPENAI_API_KEY`. Для исходного расчёта IEK или SE кнопка «Сводка» отдаёт подготовленный образец из `samples/cache/`; интерфейс показывает «Из кэша». Если параметры, данные или итоговое количество изменились, кэш может не совпасть. Тогда сводка возвращает `503` с объяснением, а числовой расчёт остаётся доступен.

## Как проверить основной сценарий

1. На macOS в терминале zsh/bash запустите команду из раздела «Установка и запуск» и откройте `http://localhost:8000`.
2. Откройте раздел **«Данные и расчёт»**, выберите **Systeme Electric** из встроенных данных `data/raw/se/`, оставьте метод «Наш расчёт» и параметры по умолчанию, нажмите **«Рассчитать»**. Затем перейдите в **«Заказы»**.
3. В поиске введите `030200193_` и откройте строку **IMT35150**. Видно **37 800 шт. в пути**, рекомендацию **22 680 шт.** и сравнение с Excel-методом **0 шт.**
4. Нажмите **«Сводка»** у поставщика: появится сохранённый текст с пометкой «Из кэша». Нажмите **«Excel для 1С»**: скачается `order_SE_<дата>.xlsx`.
5. Для проверки управляемости измените итоговое количество IMT35150 на `26 460` (семь упаковок по `3 780`) и сохраните: в строке появится `26 460`. Затем утвердите заказ. После утверждения правка блокируется; автоматической отправки поставщику нет.

Тело каждой ошибки API: `{"detail": "...", "code": "...", "meta": {}}`.

| HTTP | `code` | Ситуация |
| :-- | :-- | :-- |
| 404 | `not_found` | Нет прогона, SKU, поставщика или набора данных |
| 409 | `conflict` | Заказ уже утверждён |
| 422 | `validation_error` | Неверный JSON-параметр или отрицательное количество |
| 422 | `invalid_input` | Некратное количество или файл больше 30 МБ |
| 422 | `unknown_role`, `missing_file`, `empty_file`, `not_xlsx`, `bad_format` | Ошибка XLSX; роль файла в `meta.file_role`, когда известна |
| 503 | `unavailable` | Нет ключа LLM и подходящего ответа в кэше |
| 500 | `internal_error` | Неожиданная ошибка; детали пишутся в серверный лог |

## Бэктест

Методика и ограничения описаны в `docs/backtest.md`, исходный результат — в `data/backtest/report.json`. На шести контрольных точках с марта по август 2026 года WAPE по очищенным продажам у IEK составил **0,3972** против **0,4055** у baseline; у SE — **0,230** против **0,275**. Это проверка прогноза спроса, а не итогового заказа.

## Известные ограничения

- Прогоны и загруженные наборы живут в памяти одного процесса и исчезают после перезапуска. Утверждения сохраняются в `var/approvals.json`; пользователей и авторизации нет.
- Остаток IEK — нижняя оценка: приходы сентября неизвестны. Цен IEK в данных нет, поэтому сумма для него не показывается.
- Транзакции доступны только с 2025 года; разовые строки 2024 года нельзя проверить по документам. При загрузке без необязательного `sales_tx` анализ разовых заказов и дней наличия ограничен. Для 619 позиций ответ Laya не прошёл порог уверенности, поэтому их группа определена без модели.
- Встроенные сводки покрывают только два исходных заказа с параметрами по умолчанию. Ответы Codex нужно сверять с числовыми строками. Новые сводки требуют совместимого API, ключа и модели.
- Бэктест измеряет WAPE прогноза на горизонтах 1–3 месяца, а не экономический эффект или качество итогового заказа. Для исторических срезов используются текущие справочники SKU; внешней проверки на других данных не было.
- Автоматической отправки заказа нет. Публичный деплой не подтверждён; локальный запуск и Docker-образ подготовлены.

## Использованные внешние материалы (п. 6.4 Положения)

- Библиотеки: FastAPI, Uvicorn, Pydantic, pandas, NumPy, openpyxl, OpenAI Python SDK; React, Vite, TypeScript, TanStack Query, ApexCharts, Radix UI, Phosphor Icons, IBM Plex.
- Данные: выгрузки 1С IEK и Systeme Electric, предоставленные для кейса. Других внешних датасетов в расчёте нет.
- Открытая модель: `convaiinnovations/laya-multilingual` (Convai Innovations, Apache 2.0) предусмотрена офлайн-скриптом; в подготовленном CSV результаты её запуска отсутствуют.
- AI-инструмент разработки: Codex помогал создавать код, документацию и образцы сводок, которые затем сверены с текущим расчётом. При наличии ключа сервис вызывает модель, указанную в `MODEL`; конкретная внешняя модель в репозитории не зафиксирована.
- Готовые интерфейсные шаблоны не использовались; дизайн и стили находятся в `frontend/`.
