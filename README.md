# GrimStack — планирование заказов поставщикам

> Проект хакатона HackAlem AI. Интерфейс и расчётное ядро есть в репозитории; HTTP API и единый запуск команда ещё завершает. Mock-режим показывает зафиксированный результат реального расчёта.

## 1. Название

**GrimStack** — помощник менеджера закупок для заказов IEK и Systeme Electric.

## 2. Проблема и пользователи

Менеджер сводит выгрузки 1С вручную. Крупная разовая продажа раздувает среднее, отсутствие товара скрывает спрос, а сезонность и поставки в пути трудно учесть вместе. GrimStack показывает рекомендуемое количество и объясняет его по каждой позиции. Утверждение остаётся за человеком.

## 3. Что реализовано

- Ядро рассчитывает спрос, сезонность, тренд, страховой запас, товар в пути, остаток и кратность заказа для IEK и SE.
- React-интерфейс показывает параметры, KPI, таблицу по поставщикам, сравнение с Excel-методом, историю SKU и компоненты рекомендации.
- Есть клиентские сценарии правки количества, утверждения, загрузки файлов, экспорта и сводки. Сквозная работа ждёт HTTP API; XLSX формирует backend.
- `contracts/*.json` содержат результат реального расчёта. В `VITE_MOCK=1` это неподвижный образец: смена параметров и загрузка файлов не запускают алгоритм.

## 4. Как работает

1. Выберите поставщика, метод, срок поставки **L**, период проверки **R** и прирост спроса.
2. Нажмите **«Рассчитать»**. После загрузки своих выгрузок клиент передаёт `dataset_id` в `POST /api/runs`.
3. Сравните рекомендации с Excel-методом. Откройте SKU, чтобы увидеть историю, флаги и компоненты расчёта.
4. Измените итог с учётом кратности, утвердите заказ и скачайте XLSX для 1С. Автоматической отправки поставщику нет.

## 5. Технологии

Python 3.12, FastAPI, Pydantic, pandas, NumPy, openpyxl; React, TypeScript, Vite, TanStack Query, ApexCharts и CSS Modules. IBM Plex поставляется локально в `frontend/dist`.

## 6. Архитектура

По [проектной схеме](docs/design.md#2-архитектура) браузер загружает React SPA, FastAPI обслуживает `/api/*` и `frontend/dist` на одном порту. `ingest` читает XLSX, `engine` строит прогноз и заказ, API хранит прогоны в памяти. Опциональная сводка отделена от расчёта. Серверная точка входа и роутеры пока не слиты.

```text
XLSX → ingest → engine → RunResult → API → React → правка/утверждение → XLSX
```

## 7. Установка и запуск

Планируемый единый запуск для **macOS, терминал zsh/bash**, после добавления `app/__main__.py`:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m app
```

Ожидаемый адрес — `http://localhost:8000`; сейчас единый запуск недоступен. Текущий интерфейс можно открыть на контрактном образце:

```bash
cd frontend
npm ci
npm run dev:mock
```

`npm run build` в `frontend/` создаёт `dist`, который включён в Git.

## 8. Как проверить

Демо-SKU и ожидаемые значения описаны в [§5 проектного документа](docs/design.md#5-демо-sku-проверены-по-данным).

1. **SE 030200193_ (IMT35150):** в пути 37 800 шт., заказ 22 680 шт.; без поставки в пути он был бы 60 480 шт.
2. **IEK 130300792_ (труба Ø50):** сезонный спрос ведёт к заказу 14 800 м.
3. **SE 030200201_ (IMT35101):** наш заказ 13 560 шт., Excel-метод — 0.
4. **IEK 010300096_:** разовая строка и stockout видны в объяснении и истории. **IEK 010500006_** заказа не получает, поэтому демо «в пути» показывает SE 030200193_.

В mock-режиме эти значения зафиксированы. Для проверки влияния L, R, прироста, загрузки и экспорта нужен работающий API.

## 9. Данные и интеграции

Встроенные выгрузки 1С лежат в `data/raw/iek/` и `data/raw/se/`. Форма принимает `.xlsx` по ролям `monthly_sales`, `monthly_stock`, `sales_tx`, `in_transit`, `moq`, `seasonality`; первые четыре обязательны.

Архитектура предусматривает офлайн-классификацию товарных групп моделью **Laya** и опциональную LLM-сводку через OpenAI SDK или совместимый провайдер NVIDIA NIM. Скрипт Laya и живой вызов LLM пока отсутствуют в текущем дереве; расчёт заказа не зависит от ключа.

### Ошибки API

Контракт ответа: `{"detail": "...", "code": "...", "meta": {}}`. Подтверждённые [заданием API](docs/tasks/api.md) статусы:

| HTTP | Случай | Реакция интерфейса |
|---|---|---|
| 404 | Неизвестный прогон, SKU, поставщик или набор | Сообщение и новый расчёт для устаревшего прогона |
| 409 | Заказ уже утверждён | Перечитать прогон и заблокировать правку |
| 422 | Неверный параметр, файл или количество | Показать `detail`; `meta.file_role` привязать к полю |
| 503 | Сводка недоступна без ключа и кэша | Показать причину |

Точные значения `ErrorBody.code` ждём от владельца API (Б) и добавим в эту таблицу. Код по одному HTTP-статусу не угадываем.

## 10. Ограничения

- Нет ID клиента: прокси служит хэш номера документа-накладной.
- Транзакции доступны с 2025 года. В 2024 разовые строки не исключаются, для stockout используется доля дней по умолчанию.
- Паллетный поток SE (19 SKU, 53 % транзакций) не проходит через склад и не входит в базовый спрос.
- Остаток IEK — нижняя граница: приходы сентября неизвестны. У IEK нет цен, поэтому сумма заказа считается только для SE.
- Срок IEK выводится из дат «Пути», срок SE принимается равным 40 дням; оба параметра правятся в интерфейсе.
- Материальная ведомость 1С не предоставлена. Прогноз помесячный; дневная детализация нужна для разовых строк и доли дней в наличии.

## 11. Деплой

Развёрнутого сервиса пока нет. После деплоя Aliar добавим проверенную ссылку сюда.

## Библиотеки, модели и AI-инструменты разработки

Зависимости зафиксированы в `requirements.txt` и `frontend/package-lock.json`. Модель Laya предусмотрена архитектурой, но результат её офлайн-классификации ещё отсутствует в репозитории. Для разработки использовался Codex; числа в контрактных JSON получены расчётным ядром.
