# Frontend: инструкции для агентов

Область действия — только `frontend/**`. Источники требований: `../docs/tasks/frontend.md`, `../docs/design.md`, `../app/contracts.py`, `../contracts/*.json`. Перед реализацией прочитай их, а также `PLAN.md`, `DESIGN.md`, `design-contract.md` и `implementation-handoff.md`. `../docs/tasks/api.md` описывает поведение backend, необходимое для интеграции.

## Границы и контракт

- Изменяй только `frontend/**`. Корневой `README.md` принадлежит frontend по заданию, но обновляй его после появления работающего приложения и подтверждённой ссылки на деплой. Не меняй `app/**`, `docs/**`, `contracts/**`, `requirements.txt` и Dockerfile без согласования с владельцем.
- `src/api/types.ts` должен повторять Pydantic-модели из `app/contracts.py`. Не добавляй в сетевой запрос неописанные поля и не меняй контракт молча.
- В `docs/tasks/frontend.md` и `docs/tasks/api.md` требуется расчёт с загруженным `dataset_id`, но в текущем `RunParams` этого поля нет. Для реального API это блокер: согласуй контракт с владельцами backend и ядра, затем обнови типы и клиент. Моковый режим не является доказательством работы этой интеграции.
- Запросы делай через единый интерфейс клиента с двумя реализациями: mock при `VITE_MOCK=1` и HTTP в остальных случаях. Компоненты не должны знать, какой транспорт выбран.
- Интерфейс на русском. Числа форматируй через `Intl.NumberFormat('ru-RU')`; `null` показывай как «Нет данных», а не как `0`.
- Не показывай выдуманные продажи, цены, документы или LLM-вывод как реальные данные. У IEK цены и сумма могут отсутствовать; его остаток — оценка нижней границы.

## Визуальное направление

Рабочее место менеджера закупа: серьёзный тёмный B2B-интерфейс по `references/main-screen.png`, с плотной таблицей, четырьмя главными KPI и объяснением SKU справа. Цифры, единицы измерения, происхождение остатка и действия важнее декоративных эффектов. Дополнительный референс Adoma Trading помогает с модульностью, но его отрасль и оформление не копируются. Подробная спецификация — в `DESIGN.md`, канонические значения — в `design-tokens.json`, образцы — в `design-preview.html`. Для графиков используй `apexcharts` + `react-apexcharts` по решению пользователя; указание Recharts в более раннем задании заменено этим решением.

Сохраняй один визуальный язык на всех размерах экрана. Цвета, размеры шрифта, отступы, радиусы, высоты элементов и слои бери из токенов; при реализации отрази их в `src/styles/tokens.css`. Не задавай локальные hex-коды и случайные размеры в CSS-модулях feature. Новые блоки сначала собирай из общих компонентов `src/shared/ui/`; если нужен новый вариант, добавь его в общий компонент и предпросмотр. На 320, 390, 768, 1024, 1440 и 1920 px, а также при 200 % масштабе должны оставаться доступны все основные действия без горизонтального скролла всей страницы.

Применяй скилл по задаче, а не все сразу. Найди его в каталоге доступных скиллов Codex и прочитай `SKILL.md`. Пути установки могут отличаться на macOS и Windows.

## Рабочий порядок

1. Иди по этапам `PLAN.md`, сохраняя рабочий результат после каждого этапа.
2. Используй примеры из `../contracts/` только в mock-адаптере. Не импортируй их в live-код или production-сборку.
3. Проверяй критические пользовательские сценарии на реальном API после его появления: расчёт, PATCH, утверждение, экспорт, история SKU, загрузка и сводка.
4. Перед готовностью к выпуску проверь сборку `frontend/dist`, клавиатурную навигацию, все ширины из `DESIGN.md`, 200 % масштаб, отсутствие визуальных дублей общих компонентов и отсутствие моковых данных в production-бандле.

Команды для macOS выполняй в стандартном терминале zsh/bash. Коммиты, если их попросили, оформляй по пользовательскому формату Conventional Commits на русском с обязательным body по каждому затронутому файлу.
