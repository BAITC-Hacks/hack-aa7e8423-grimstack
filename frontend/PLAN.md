# Frontend закупок — план разработки

> **Для исполнителя:** выполняй задачи последовательно по этому документу и `AGENTS.md`. Для пошаговой реализации можно использовать `superpowers:executing-plans`; создание отдельных агентов не требуется.

**Цель:** подготовить полноценный интерфейс менеджера закупа на Vite + React + TypeScript, работающий сначала с контрактными моками, затем с FastAPI без переписывания компонентов.

**Архитектура:** одна React SPA, один экран результатов и боковая панель SKU. Компоненты обращаются к типизированному `ProcurementApi`; реализация выбирается по `VITE_MOCK=1`. FastAPI в выпуске отдаёт `frontend/dist` и `/api/*` с одного origin.

**Спецификация:** `../docs/tasks/frontend.md`, `../docs/tasks/api.md`, `../docs/design.md` (§1, §2, §5–7, §11), `../app/contracts.py`, `../contracts/*.json`, `../docs/data-profile.md`. Визуальные решения — `DESIGN.md` и `references/main-screen.png`; дополнительный референс — Adoma Trading.

**Приоритет на текущем этапе:** этап 0 пропущен; сначала рабочие этапы 1 → 2 → 3 → минимальный 4, затем загрузка и сводка из этапа 5. Каркас, клиент, параметры L/R/прирост, таблица, PATCH, утверждение, API-экспорт, график, «лесенка», форма загрузки и сводка реализованы на уровне интерфейса. `dist` собран и закоммичен. Сквозная проверка с живым API ждёт серверные роутеры; адаптивность и VoiceOver проверяются после неё.

## Общие ограничения

- Менять только `frontend/**`; корневой `README.md` обновить на финальном этапе по заданию frontend.
- Интерфейс на русском, числа через `Intl.NumberFormat('ru-RU')`, графики через ApexCharts с React-обёрткой, dev-прокси `/api` на `http://localhost:8000`. Более раннее указание Recharts в `docs/tasks/frontend.md` заменено прямым выбором пользователя.
- TypeScript-типы должны соответствовать `app/contracts.py`; Python-контракт заморожен до согласования всех владельцев.
- Сборка `frontend/dist` входит в репозиторий и раздаётся FastAPI. Команды разработки и сборки выполнять в терминале macOS zsh/bash.
- Реальные и демонстрационные данные должны быть визуально различимы; моковый режим не подтверждает корректность алгоритма.
- Все экраны и состояния используют `design-tokens.json` и общие компоненты `src/shared/ui/`; responsive-правила и контрольные размеры описаны в `DESIGN.md`.

## Что особенно проверить на ревью

| Условие | Ожидаемое поведение и этап проверки |
|---|---|
| `null` в цене, сумме, прогнозе или сравнении | «Нет данных»/«Нет цены», без ложного нуля; этапы 2–4 |
| Два поставщика с разными default L/R | `null` в общих параметрах, backend применяет defaults каждого; этапы 2 и 6 |
| Дробная кратность и нулевое итоговое количество | Нет ошибок округления; 0 принимается, некратное значение даёт понятный 422; этапы 3 и 6 |
| Утверждение во время редактирования строки | 409 обновляет статус и не оставляет в UI несохранённое количество; этапы 3 и 6 |
| Перезапуск backend при сохранённом `run_id` | 404 сбрасывает устаревший результат и предлагает новый расчёт; этапы 2 и 6 |
| 320 px, длинное название или 200 % масштаб | нет горизонтального скролла страницы; расчёт, правка, утверждение и экспорт остаются доступны; этапы 0, 3 и 7 |

## 0. Справка о состоянии проекта

Frontend-приложение собрано. `contracts/*.json` сгенерированы из реального расчёта и используются как неподвижный образец для mock-режима. Backend API разрабатывается отдельно; переключение параметров в mock-режиме не запускает алгоритм.

**Текущее состояние контракта:** `RunParams` в `../app/contracts.py` уже содержит `dataset_id: str | None = None`. Frontend передаёт идентификатор после загрузки. Сквозная приёмка остаётся открытой до проверки, что backend действительно использует загруженный набор в расчёте.

Ещё две договорённости нужны для точной интеграции:

1. `PATCH /lines/{line_id}` возвращает только `OrderLine`, хотя backend пересчитывает суммы. После PATCH frontend перечитывает `GET /api/runs/{run_id}` для актуальных KPI и сводки поставщика.
2. Для режима «все поставщики» поля L/R должны оставаться `null`, чтобы каждый поставщик получил собственный default. Категория в этом режиме скрыта/недоступна, поскольку списки категорий IEK и SE различаются.

## 1. Технический выбор

| Роль | Решение | Причина |
|---|---|---|
| Основа | Vite, React, TypeScript со строгой проверкой типов | Требование задания, быстрый dev-сервер и одна статическая сборка |
| Серверное состояние | `@tanstack/react-query` | Запросы, повторные загрузки и обновление результата после PATCH/approve |
| Таблица | `@tanstack/react-table` | Контроль сортировки, фильтров и пагинации при свободной B2B-вёрстке |
| История и водопад | `apexcharts` + `react-apexcharts` | Выбор пользователя для графиков; один графический стек |
| Модальные окна и подсказки | `radix-ui` Primitives | Управление фокусом, Escape и клавиатурой без навязанного визуального стиля |
| Стили | CSS Modules + общие CSS-переменные | Полный контроль плотной таблицы и визуальной системы без второго UI-фреймворка |
| Иконки | `@phosphor-icons/react` | Одна сдержанная система пиктограмм; подписи остаются видимыми |
| Шрифт | `@fontsource/ibm-plex-sans` и `@fontsource/ibm-plex-mono`, только нужные начертания | Читаемость плотных данных и воспроизводимость без внешнего CDN |
| XLSX | Экспорт через backend API | Файл содержит сохранённые количества; клиентский mock-экспорт не нужен |
| Проверка при реализации | Vitest, React Testing Library; браузерная проверка ключевых сценариев | Проверяются действия пользователя и контракт клиента |

Не добавлять Redux, роутер, анимационную библиотеку, Tailwind и отдельный UI-kit: в текущем одноэкранном продукте они добавят настройку и пересекающиеся правила. Пакеты и их актуальные API проверить по официальной документации при установке; версии закрепить в lock-файле.

## 2. Дизайн-контракт

Полные правила находятся в `DESIGN.md`, значения токенов — в `design-tokens.json`, статический образец блоков — в `design-preview.html`, происхождение решений — в `design-contract.md`, короткая передача исполнителю — в `implementation-handoff.md`. Главный референс — приложенный пользователем тёмный макет `references/main-screen.png`; Dribbble-работа служит дополнительным примером модульного B2B-интерфейса.

Первый экран: компактные параметры и «Рассчитать» сверху; **четыре главных KPI** под ними; группы IEK и Systeme Electric с таблицами; после выбора строки — панель истории и «лесенки» справа. Два остальных KPI контракта остаются доступны во вторичном контексте. Тёмная палитра, сдержанные состояния и типографика из `DESIGN.md` заменяют прежнюю светлую концепцию.

В демонстрации жюри нужно пройти путь: расчёт ассортимента двух поставщиков → труба Ø50 с сезоном и stockout → IMT35101 с расхождением нашего и Excel-метода → возврат к нашему методу → правка количества → утверждение → XLSX. Числа из мокового JSON показываются как демонстрационные; после подключения backend используются только реальные результаты ответа.

## 4. Этапы реализации

### Этап 0. Фиксация дизайн-системы

**Файлы:** `DESIGN.md`, `design-tokens.json`, `design-preview.html`.

- [ ] Сверить `DESIGN.md`, JSON-токены и статический предпросмотр: значения цветов, типографики, отступов и радиусов должны совпадать.
- [ ] Открыть предпросмотр на 320, 390, 768, 1024, 1440 и 1920 px. Поправить композицию, если она не помещается; не снижать размер текста ниже установленной шкалы.

**Результат:** единый визуальный контракт готов до написания компонентов.

### Этап 1. Каркас и типизированный клиент

**Файлы:** `package.json`, конфигурации, `src/main.tsx`, `src/App.tsx`, `src/api/*`, `src/styles/*`.

- [ ] Создать Vite React TS внутри `frontend/`, включить строгий TypeScript и команды `dev`, `build`, `typecheck`, `lint`.
- [ ] Перенести значения `design-tokens.json` в `:root` файла `tokens.css`. Для типографики, цветов, поверхностей, отступов, радиусов, высоты контролов и z-index использовать только эти переменные; новые значения сначала добавлять в JSON и CSS вместе.
- [ ] Реализовать общие `PageShell`, `SectionPanel`, `Button`, `Field`, `Select`, `StatusBadge`, `KpiMetric`, `Dialog`, `Tooltip`, `Skeleton`, `InlineAlert`. Варианты и состояния брать из `DESIGN.md`; feature-компоненты их собирают, не рисуют копии.
- [ ] Задать responsive-сетку по четырём диапазонам из `DESIGN.md`. При 1440+ панель деталей занимает правую колонку; ниже она накладывается; под 640 px строки становятся карточками и панель открывается на весь экран.
- [ ] Настроить `/api` → `http://localhost:8000` только в dev и `server.fs.allow` для `../contracts` без открытия всего домашнего каталога.
- [ ] Перенести все модели `app/contracts.py` в `src/api/types.ts`: `null`, литералы, даты как строки ISO; `line_id` считать стабильным ключом.
- [ ] Задать интерфейс `ProcurementApi`: `getMeta`, `createRun`, `getRun`, `patchLine`, `approveSupplier`, `exportXlsx`, `getSkuHistory`, `uploadDataset`, `getSummary`.
- [ ] Реализовать `liveClient` на относительных `/api/*`, разбор `ErrorBody`, кодов 404/409/422/503, запрос XLSX как `Blob`, правильное кодирование SKU и `line_id` в URL.
- [ ] Реализовать `mockClient` с копией JSON-фикстур и имитацией задержки. PATCH меняет строку и итоги, approve меняет статус и блокирует PATCH; экспорт XLSX выполняет backend API. Историю, отсутствующую в образце, показывать как недоступную, не генерировать вымышленные продажи.
- [ ] Убедиться, что production-сборка с `VITE_MOCK` выключенным не содержит моковые JSON и не обращается к `../contracts`.

**Результат:** приложение открывается, данные мета и прогона доступны через один интерфейс клиента; смена транспорта не требует правок UI.

### Этап 2. Параметры и расчёт

**Файлы:** `features/parameters/*`, `features/overview/*`, `shared/format.ts`.

- [ ] При открытии загрузить `/api/meta`; от него построить селектор поставщика и категории. При «все» категория недоступна, L/R отправляются как `null`.
- [ ] Сделать форму с полями метода, L/R (1–365 дней или `null`), уровня сервиса (`0.5 < x < 1`, в UI ввод в процентах с преобразованием), прироста (`−90…500 %`). Плейсхолдеры L/R брать из `Meta.suppliers`.
- [ ] По «Рассчитать» вызвать `POST /api/runs`; до результата показывать skeleton, при ошибке — `detail` и «Повторить», при пустом списке — «Заказывать нечего».
- [ ] Вывести четыре главных KPI как на макете и два дополнительных показателя во вторичном блоке, сохранив все поля `RunResult.kpi`; показать `data_as_of`, метод и список `warnings`. Сумму IEK не подменять нулём.
- [ ] Сохранять `run_id` в `sessionStorage` только как ссылку на серверный прогон. При 404 после перезапуска backend безопасно сбрасывать текущий прогон и предлагать новый расчёт.

**Результат:** пользователь может получить и прочитать результат расчёта без таблицы.

### Этап 3. Рабочая таблица заказа

**Файлы:** `features/orders/*`, `shared/quantity.ts`, `shared/download.ts`.

- [ ] Сгруппировать `RunResult.lines` по `supplier`, используя `RunResult.suppliers` для заголовка и статуса. Отсортировать `critical → high → planned → none`, затем по сумме у SE; `null` в конце, стабильный tie-breaker по SKU.
- [ ] На первом уровне таблицы показать товар, остаток, наш заказ/итог, Excel и срочность как на макете. Остальные обязательные поля из задания доступны через настройку колонок и панель SKU. Добавить локальный поиск по коду/артикулу/названию и фильтр срочности; для больших результатов включить пагинацию.
- [ ] Вывести `baseline_qty` и разницу с `recommended_qty`. `null` отображать как отсутствие сравнения. Источник остатка и `approx_stock` показывать рядом с числом, включая текстовую подсказку.
- [ ] Сделать поле `final_qty`: допускается 0; отрицательные и некратные MOQ значения подсвечиваются до отправки, а ответ 422 показывается у ячейки. Сохранять по явной кнопке или Enter, отменять черновое изменение по Escape.
- [ ] После PATCH обновить строку и запросить свежий `GET /api/runs/{run_id}` для KPI и итогов. Во время запроса блокировать повторное сохранение этой строки. На 409 сообщить, что заказ уже утверждён, и перечитать статус.
- [ ] Утверждение поставщика делать отдельной кнопкой с ясным подтверждением выбранного поставщика. После успеха сделать его строки только для чтения и показать дату утверждения.
- [ ] Экспорт скачать как XLSX с именем из `Content-Disposition` либо `order_<supplier>_<date>.xlsx`. Ошибку скачивания показывать в интерфейсе, object URL освобождать.

**Результат:** состав заказа можно изменить, утвердить и выгрузить; все итоги соответствуют серверу.

### Этап 4. Панель SKU и объяснимость

**Файлы:** `features/sku/*`, общие диалоги и подсказки.

- [ ] По открытию строки лениво запросить историю по `supplier + sku`, показать отдельные загрузку/ошибку/отсутствие истории.
- [ ] Через ApexCharts объединить `months` и `forecast_months` в одну ось. Показать `raw`, переключаемые `cleaned`/`restored`, пунктирный `forecast`, заштрихованные исторические месяцы stockout и точки `oneoff_events` с датой/количеством.
- [ ] Сделать управляемую легенду и текстовую таблицу значений, чтобы различия были доступны без цвета и без графика.
- [ ] Разделить `components`: `qty` — числовая «лесенка» с направлением плюс/минус и итогом `recommended_qty`; `factor` — множители; `info` — справочные величины. Не складывать множители и справочные значения с количеством.
- [ ] Вывести полный `explanation`, флаги с русскими подписями, цену/сумму только когда данные есть. На мобильном панель становится полноэкранной.

**Результат:** для SKU видна история и путь от прогноза к заказу; пример `IEK:010300096_` из JSON показывает разовую строку и stockout.

### Этап 5. Загрузка и сводка

**Файлы:** `features/datasets/*`, `features/summary/*`.

- [ ] Сделать форму загрузки для одного поставщика: `monthly_sales`, `monthly_stock`, `sales_tx`, `in_transit` обязательны; `moq`, `seasonality` необязательны. Проверять `.xlsx`, непустой файл и предел 30 МБ на клиенте, оставляя сервер источником истины.
- [ ] Отправлять multipart с именами полей, равными ролям. 422 с `meta.file_role` показывать у нужного поля; общую ошибку — над формой. После успеха показать `warnings` и `dataset_id`. Mock-ответ должен прямо сообщать, что файлы не разбирались, а расчёт использует образец.
- [ ] Не заявлять в live-режиме, что загруженные данные участвуют в расчёте, пока это не пройдёт сквозную проверку. В mock-режиме помечать загрузку как демонстрацию интерфейса.
- [ ] Для сводки вызвать `POST /api/runs/{id}/summary?supplier=…`, показать ответ в модалке и метку «Из кэша» при `cached=true`. На 503 показать причину без падения экрана.
- [ ] Учитывать `Meta.llm_available` в подписи действия: отсутствие live LLM не исключает наличие кэша, поэтому запрос разрешён, а недоступность определяется ответом 503.

**Результат:** формы и состояния готовы; сквозная загрузка ждёт работающего backend API.

### Этап 6. Подключение реального API

**Файлы:** `src/api/*`, при необходимости только связанные компоненты.

- [ ] Сверить `/api/meta`, `POST /api/runs`, `GET /api/runs/{id}` и историю SKU с фактическими ответами backend. Любое расхождение сначала обсудить с владельцем контракта.

### Этап 7. Выпуск и документация

**Файлы:** `frontend/dist/**`, `../README.md` после появления работающего продукта и ссылки на деплой.

- [ ] Проверить, что исходный mock JSON, приватные XLSX, ключи и секреты не попали в `dist`; что запросы `/api/*` относительные и работают на адресе деплоя.
- [ ] Сверить загрузку `frontend/dist` через `python -m app`, скачанный XLSX открыть в Excel/LibreOffice, проверить дату и содержимое.
- [ ] Обновить корневой README по 11 пунктам `docs/tasks/frontend.md`, описать реальное состояние интеграций и ограничения §11 `docs/design.md`. Добавить ссылку на деплой после получения от backend-владельца.
- [ ] Закоммитить `dist` согласно заданию проекта и проверить запуск из чистого клона.

**Критерий готовности frontend к выпуску:** все действия работают с реальным API; нет моков в production-бандле; загрузка влияет на расчёт; таблица, график и формы доступны на узком экране и с клавиатуры; экспорт содержит сохранённые итоговые количества; интерфейс честно показывает оценки и отсутствующие цены.

**Критерий готовности всей системы к production:** отдельно подтвердить поведение backend при рестарте, защиту доступа к заказам и загружаемым файлам, сохранность данных, ограничения размера запросов и безопасную конфигурацию деплоя. Нынешний дизайн предусматривает прогоны в памяти и утверждения в JSON, поэтому готовность frontend сама по себе не означает готовность сервиса к постоянной эксплуатации.
